# 事故・ヒヤリハットの記録

> 起きたことを**事実ベースで**残し、再発防止のルールを AGENTS.md の該当 § に反映する。
> ルールには「なぜあるか」が必要で、その出典がこのファイルになる。新しいものを上に追記する。
> 2026-11-27 に、AGENTS.md と docs/agents/ の各章に散らばっていた記録を集約した（各章の記述は残している）。

## 書き方

```markdown
## YYYY-MM-DD 〈一行の要約〉

- **何が起きたか**: 観測された事実（いつ・どこで・何が）。
- **影響**: 誰に・どの範囲で。取り消せたか。
- **原因**: 直接の原因と、それを許した仕組みの穴。
- **再発防止**: 追加 / 変更したルール（AGENTS.md §N）・スクリプト・テスト。
```

## 2026-11-27 自動デプロイが、前提の安全ガードを入れないまま有効になっていた

- **何が起きたか**: `auto-deploy.sh`（5 分ごとの cron）は「dirty な作業ツリーなら中止・staging は `staging` ブランチへ反映、のガードを入れるまで有効化しない」方針（§7.6・回帰テスト [18] のコメント）だったが、PR #106 で実行権限が付き、ガードの無いまま動いていた。調査で次が分かった（実害の発生は未確認）:
  - 本番ツリーを `git reset --hard origin/main` で無条件に上書きしていた。未コミットの変更や、push に失敗して溜まった cron のデータコミットがあれば消えていた。
  - staging ツリーを、チェックアウト中のブランチ（`docs/node-version-check`）のまま main に上書きし続け、§14.1 の「`staging` ブランチ固定」が崩れていた（外部評価で「staging ツリーが雑用チェックアウト化」と指摘）。
  - CI の結果を見ずに本番へ出していた。ワーカーを再起動せず、ワーカー側の変更が反映されていなかった。
  - 失敗したコミットを 5 分ごとに再試行し、再起動と通知を繰り返す作りだった。多重起動の防止も無かった。
  - Discord の Bot トークンを curl のコマンド引数に渡していた（`ps` から見える）。
- **原因**: 有効化の前提条件が文書（コメント）にしか無く、実行権限を付ける変更でそれを確かめる仕組みが無かった。
- **再発防止**: 上記をすべて修正し、判定テスト `scripts/ci/test-auto-deploy.sh` を CI に追加（§7.3.6）。

## 2026-11-27 pre-push が「今いるブランチ名」で判定しており、別名での main への push を通していた

- **何が起きたか**: PR #114 の独立レビューで、`git push origin agent/x:main` や、作業ブランチ上での `git push origin main` が pre-push の保護をすり抜けることが分かった（実害の発生は確認されていない）。
- **原因**: `git branch --show-current` で判定しており、git が標準入力で渡す実際の push 先を見ていなかった。
- **再発防止**: push 先の ref で判定するよう変更し、判定テスト `scripts/ci/test-pre-push.sh` を CI に追加（PR #115・§14.2）。

## 2026-11-27 日次 cron の自動 push が pre-push に拒否され、データのコミットが溜まっていた

- **何が起きたか**: `update-subscribers-and-commit.sh`（毎日 00:05）の `git push` が pre-push の「main への直接 push は禁止」で拒否され、2026-11-24〜27 の 4 回分のデータコミットが本番ツリーに溜まっていた（`logs/subscribers.log` で確認）。ログにはエラーが出ていたが、誰も気づかなかった。
- **原因**: 2026-10-25 に pre-push へ「main への直接 push を拒否」を入れた際、cron 用の例外フラグ `SKIP_PREPUSH=1` を cron スクリプト側に付けていなかった。失敗はログに残るだけで通知されない。11-23 以前の分が拒否されずに済んでいた理由は未確認。
- **再発防止**: cron スクリプトに `SKIP_PREPUSH=1` を付与（§7.5）。`SKIP_PREPUSH=1` は cron 専用と明記し、エージェントが手作業で使うことはガードで拒否（§13）。

## 2026-11-27 運用ルール（§13 と §14.1）の矛盾を根拠に、main へ直接 push した

- **何が起きたか**: §13 の「小さな修正は直接 push 可」を根拠に、エージェントが `SKIP_PREPUSH=1` で main へ 3 回直接 push した（データ更新・不要ファイル整理・cron 修正）。§14.1 は直接 push を禁止していた。
- **原因**: 文書どうしが矛盾しており、機械的な強制（pre-push）を例外フラグで回避できた。
- **再発防止**: §13 を §14.1 に合わせて「すべて PR 経由」に統一（PR #110）。手作業の `SKIP_PREPUSH=1` と `--no-verify` をエージェント用ガードで拒否（§13）。

## 2026-11-27 秘密値を含む nginx.conf とそのバックアップが全ユーザーから読めた

- **何が起きたか**: nginx テンプレート移行のレビューで、`TAILNET_ADMIN_SECRET` を含む `/etc/nginx/nginx.conf` と `nginx.conf.bak-*` が 0644 で配置されていることが分かった。生成スクリプトも、照合のために秘密値をコマンド引数に渡していた（`ps` から見える）。
- **原因**: 配置時の権限を指定していなかった。バックアップは `cp -a` で元の権限を引き継いでいた。
- **再発防止**: `nginx.conf` とバックアップを 0600 で配置し、照合は組み込みの `printf` から渡す（PR #113、`scripts/nginx/templates/README.md`）。

## 2026-10-24 共有の作業ツリーでブランチを切り替え、他セッションの作業を壊した（2 回）

- **何が起きたか**: 複数のセッション（エージェント含む）が同じ作業ツリーを使い、ブランチの切り替えで staging アプリのコードが入れ替わった。また、PR に無関係なコミットが混入した（PR #83）。
- **原因**: 作業ツリーが物理的に分かれていなかった。
- **再発防止**: per-session worktree を必須化し、canonical staging tree を `staging` ブランチに固定（§14）。PR 本文に「含むべきファイル一覧」を書き、レビュアーが `git diff --stat` で混入を検出する。

## 2026-10-24 push エンドポイント検査の無効化時に、全通知が黙って止まる状態だった

- **何が起きたか**: 独立レビューで、`PUSH_GUARD_DISABLED=1` のとき判定関数が `ReferenceError` を起こし、例外が握りつぶされて全通知が送られない状態だったことが分かった。
- **原因**: 判定関数をクロージャ内に置いていた。無効化経路を実際に動かすテストが無かった。
- **再発防止**: 判定関数をモジュールスコープへ移し、無効化インスタンスで `check()` を実際に呼ぶ回帰テストを追加（§11）。

## 2026-10-23 依存更新の反映中に、本番 3 プロセスが止まったままになった

- **何が起きたか**: `npm-deploy.sh` が pm2 を停止して `npm install` した後、ロード確認が exit 1 で終了し、`mai-push-api` / `mai-push-worker` / `discord-bot` が再起動されないまま残った。
- **原因**: 再起動がスクリプトの最後にしかなかった。ロード確認が firebase-admin v14 で廃止された API を検査しており、更新が成功しても必ず失敗した。
- **再発防止**: `trap ... EXIT` で必ず再起動する。ロード確認を新しい API の検査に更新（§5）。

## 2026-10-20 / 10-21 umask 077 のシェルで本番ツリーを書き換え、PHP が 500 / 403 になった

- **何が起きたか**: `umask 077` のシェルで本番ツリーの `git pull`（10-20）と `git checkout --`（10-21）を行い、書き換わったファイルが mode 600 になった。php-fpm（www-data）が読めず、`/logs/` が 500、トップページが 403・CSS が 404 になった。
- **原因**: 作業者のシェルの umask が厳しく、git がそれに従ってファイルを作った。
- **再発防止**: `promote.sh` / `deploy-staging.sh` で `umask 002` を固定。`verify-deploy.sh` が other 読み取り不可を検出して exit 1（§7.1）。

## 2026-10-13 / 10-14 WinUI アプリが起動しない（ネットワークドライブ・旧版の残骸）

- **何が起きたか**: (1) `Q:\` のネットワークドライブから起動すると WebView2 が `COMException` で描画されなかった（2 回目）。(2) v1.8.0 のインストール後、「.NET が無い」として起動しなかった。
- **原因**: (1) WebView2 がネットワーク共有から読めない。(2) インストール先に旧版の .NET ランタイム DLL が残り、ホストがアプリのフォルダを自己完結型の .NET ルートと誤認した。
- **再発防止**: (1) ビルド出力をローカルドライブに固定（§10）。(2) インストーラーで導入前に `{app}` を全削除（`Windows/mai-push-winui/installer.iss`）。

## 2026-09-26 LF → CRLF の混入で作業ツリーが dirty になった

- **何が起きたか**: main.js を含む 8 ファイルに CRLF が混入し、作業ツリーが dirty になった。
- **再発防止**: `.gitattributes` で `text=auto eol=lf`（§7.7）。

## 2026-09-19〜27 nassy の DL サーバーを手動起動のまま 9 日間放置した

- **何が起きたか**: `download.py` を手動起動したまま放置し、(1) 標準出力がどこにも残らずログが失われた、(2) 9/21 に更新した新コード（DL 後処理）が反映されないまま動き続けた。
- **原因**: プロセス管理（systemd）を使わず手動で起動していた。
- **再発防止**: systemd user unit 化し、手動起動を禁止（§8）。

## 2026-09 下旬 本番と staging の取り違え、本番通知 API への誤送信

- **何が起きたか**: (1) `curl localhost:8081` を本番と思い込み、staging の旧コードを本番と誤認した。(2) 本番（8080）の `/api/notify` にテスト送信し、実ユーザーへ通知が誤配信された（取り消し不能）。
- **原因**: ポートの思い込み。テストを本番に向けられる状態だった。
- **再発防止**: 操作の前にポートの持ち主を確認する `assert-port.sh`（§1・§7.2）。通知の確認は staging（`DISABLE_NOTIFICATIONS=1`）でのみ行う（§2）。回帰テストの本番ポート拒否。エージェント用ガードで本番 `/api/notify` への送信を拒否（§13、2026-11-27）。
